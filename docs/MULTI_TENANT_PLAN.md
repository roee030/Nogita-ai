## סטטוס שלב A (30.10)

נעשה, בלי לשנות את ההתנהגות של התקנה קיימת שמוגדרת דרך env:

- **`TenantConfig`** ([tenant-config.ts](../src/app/tenant-config.ts)) הוא אובייקט אחד לכל חברה: לוחות, ריפואים, צ'אט, אנשים, הרשאות ו-AI.
  - הוא נבנה מ-env כמו קודם, או מקובץ JSON שמוגדר ב-`NOGITA_TENANT_CONFIG`.
  - סודות בקובץ הם הפניות (`"env:NAME"`), לא ערכים.
  - שגיאה בקובץ אומרת איזה שדה שגוי ולא מדפיסה סוד.
  - דוגמה: [config/tenant.example.json](../config/tenant.example.json).
- **רישום חיבורים** ([multi.ts](../src/adapters/multi.ts)):
  - `MultiBoard` ו-`MultiCode` מציגים כמה לוחות וכמה ריפואים מאחורי אותם פורטים, כך שהמנוע לא השתנה.
  - משימה הולכת ללוח ברירת המחדל או ללוח שנאמר בשמו.
  - אדם נשאר משויך ללוח שבו נמצא.
  - נתיבי קוד מתחילים בשם הריפו ("shop/src/...").
- **חיפוש משימות כללי:** ל-`TaskSearch` יש טקסט, סטטוס, אחראי, לא משויך ולוח. Jira מתרגם את זה ל-JQL.
  ה-JQL הגולמי מוצע למודל רק כשיש לוח Jira.
- **ערכות conformance** ([tests/conformance/kits.ts](../tests/conformance/kits.ts)):
  - כל לוח וכל ריפו עוברים אותה בדיקה.
  - רצים עכשיו: MemoryBoard, Jira (מול fake עם מצב), MultiBoard (בשני צירופים), MemoryCode ו-MultiCode.
  - הערכה כבר תפסה באג אחד: `MultiBoard` החזיר רשימה ריקה ל-JQL כשאף לוח לא הבין JQL, והמודל היה מסיק "אין משימות".
- **הבדיקות:** 390 מתוך 390 עוברות (45 חדשות).

## ההחלטה המרכזית: איך מבודדים

| | תא נפרד לכל חברה (מומלץ) | שרת משותף לכולם |
|---|---|---|
| בידוד | מלא: תהליך, דיסק, מפתחות וסודות נפרדים. באג לא יכול לדלוף לחברה אחרת | בקוד בלבד. באג אחד יכול לחשוף נתונים |
| כמה עבודה | מעט. הקוד כבר "חברה אחת לשרת" | הרבה. כל ה-Maps הגלובליים ב-`server.ts` צריכים לקבל tenant |
| עלות לחברה | שרת קטן ודיסק, בערך 10 עד 25 דולר בחודש | זול יותר בקנה מידה גדול |
| מה מוכרים לארגון גדול | "הנוגיטה שלכם רצה לבד" | צריך להסביר |

**המלצה: תא (cell) לכל חברה, ומעליו "מגדל שליטה" אחד משותף.**
- **התא** הוא הנוגיטה של היום, כמעט בלי שינוי: שרת אחד, דיסק קבוע ומפתח הצפנה משלו.
- **מגדל השליטה** הוא אתר ההרשמה, אשף החיבורים, שירות ה-OAuth, הקמה ומחיקה של תאים, ניתוב webhooks משותפים וחיוב.
  הוא לא רואה תמלולים, קוד או משימות. הוא מחזיק רק מי הלקוח, איזה תא שלו והפניות לסודות.

אם בעתיד יהיו מאות לקוחות קטנים, אפשר להריץ כמה תאים על אותו מחשב (container לכל אחד). הבידוד נשאר, והעלות יורדת.

## איך נראית התקנה (היעד: 10 דקות, בלי מהנדס)

1. **הרשמה:** כניסה עם חשבון Google או Microsoft של העבודה. החברה נוצרת ותא מוקם אוטומטית, תוך דקה או שתיים.
2. **אשף חיבורים:** כפתור לכל כלי ("Add to Slack", "Connect Jira", "Install GitHub App", "Connect Teams"...).
   כל חיבור הוא OAuth בלחיצה, ואחריו בוחרים פרויקטים, לוחות וריפואים. מה שהחברה לא משתמשת בו, מדלגים עליו.
3. **אנשים:** אחרי החיבור, נוגיטה מתאימה אנשים לפי אימייל בין Slack, Jira, GitHub והחשבון של הארגון. האדמין רואה רשימה
   מוכנה ומסמן מי רשאי לבקש ממנה שינויים. אין יותר JSON ידני.
4. **פגישות:** מחברים יומן (אופציונלי), והיא מצטרפת לפגישות שמזמינים אליהן את `nogita@<החברה>`. או מדביקים קישור.
   כפתור "נסה עכשיו" שולח אותה לפגישת ניסיון.
5. **דף בריאות:** כל חיבור נבדק חי (הבדיקות של `/api/connections` כבר קיימות), עם הסבר מה לתקן.

## השלבים

### שלב A: התא מוכן להיות של לקוח (בלי מגדל שליטה, אפשר להתחיל עכשיו)

1. **קונפיגורציה כאובייקט אחד:** `TenantConfig` במקום קריאות מפוזרות ל-`env`. נטען מקובץ מוצפן או משירות סודות,
   ומשתני סביבה ממשיכים לעבוד לפיתוח. `createDependencies(config)` מקבל אותו.
2. **רישום חיבורים (registry):** כמה לוחות, ריפואים וערוצים לכל חברה. לכל connector יש יכולות מוצהרות (search, create,
   assign, comment), והכלים של המודל נבנים לפי מה שמחובר בפועל. זה גם מה שתוכנן ב-`ARCHITECTURE.md`.
3. **חיפוש משימות כללי:** `TaskSearch` עם פילטרים (טקסט, סטטוס, אחראי, פרויקט). כל adapter מתרגם אותם לשפה שלו
   (JQL, GraphQL של Linear, WIQL של Azure). JQL נשאר כאפשרות מתקדמת ל-Jira בלבד.
4. **התאמת אנשים אוטומטית לפי אימייל**, עם רשימה שהאדמין מאשר. נשמרת בתא.
5. **אחסון קבוע חובה** לכל תא, ומפתח הצפנה משלו. בלי זה התא לא עולה (`readiness` כבר בודק את זה).
6. **ערכת בדיקות התאמה (conformance) לכל פורט:** כל adapter חדש עובר את אותן בדיקות מול stub, ואז רשימת בדיקה חיה.
   כך מוסיפים כלים מהר בלי לשבור כלום.

### שלב B: מגדל השליטה

1. **הרשמה וחשבון חברה:** Google ו-Microsoft SSO, ותפקידים (אדמין וחבר צוות).
2. **שירות OAuth:** אנחנו רושמים פעם אחת אפליקציה בכל ספק (Slack app, Atlassian, GitHub App, Google, Microsoft/Teams,
   Zoom, Linear, monday, Asana...). כל חברה מתקינה אותה אצלה, הטוקנים שלה נכנסים לסודות של התא שלה בלבד, ו-refresh מתבצע אוטומטית.
3. **הקמת תא:** מאחורי ממשק `Provisioner`, כך שאפשר להחליף ספק. הגרסה הראשונה דרך ה-API של Render (כבר בשימוש),
   עם אופציה ל-Fly.io Machines או Kubernetes. מחיקת חברה: התא נהרס, הטוקנים מבוטלים, הדיסק נמחק.
4. **ניתוב webhooks משותפים:** אפליקציה אחת של Slack או Teams שולחת אירועים לכתובת אחת. המגדל בודק חתימה ומעביר לתא הנכון
   לפי `team_id` או `tenant_id`, בלי לשמור את התוכן. בוטים של פגישות (Attendee/Recall) מקבלים webhook ישירות לכתובת של התא.
5. **שימוש וחיוב:** שעות פגישה, שימוש במודל ומשימות לכל חברה. `session-usage` כבר מודד, וצריך לרכז את המספרים במגדל.

### שלב C: כל הכלים (לפי סדר ערך)

| עדיפות | כלי | מה צריך | הערות |
|---|---|---|---|
| 1 | Slack OAuth, Atlassian OAuth (Jira), GitHub App | להפוך את מה שקיים להתקנה בלחיצה | GitHub App גם מגביל לריפו נבחר (`architecture-next.md` סעיף 6) |
| 2 | Microsoft Teams: פגישות | דרך Attendee או Recall, כמו Meet | לבדוק קול בזמן אמת ו-chat ב-Teams |
| 2 | Microsoft Teams: הודעות | Azure Bot, אפליקציה multi-tenant, admin consent | בלי הרשאת קריאה לערוץ, Teams שולח רק הודעות עם mention |
| 3 | Zoom | דרך Attendee או Recall | לבדוק: Attendee כנראה דורש Zoom app משלנו, Recall לא |
| 3 | Linear, monday (מלא), Azure DevOps, GitHub Issues | `BoardPort` מלא + conformance | monday: מיפוי עמודות של אחראי, סטטוס ותיאור |
| 4 | GitLab, Bitbucket | `CodePort` (קריאה, חיפוש, commits) | |
| 4 | Google Calendar, Outlook | הצטרפות אוטומטית לפגישות שהיא הוזמנה אליהן | רק אחרי opt-in מפורש |
| 5 | Asana, ClickUp, Trello, Google Chat, Discord, Webex | לפי ביקוש של לקוחות | |

כל connector חדש בנוי באותה תבנית: adapter מאחורי הפורט, stub לבדיקות, ערכת ה-conformance, בדיקת חיבור חיה לדף
הבריאות, ומסך OAuth באשף.

## בטיחות ופרטיות לכל חברה

- **סודות:** לכל תא שירות סודות משלו עם מפתח משלו. המגדל מחזיק הפניות בלבד.
- **רשת:** תא לא יכול לפנות לתא אחר. רק המגדל מעביר אליו אירועים חתומים.
- **הרשאות:** כל טוקן בהיקף המינימלי. בקוד: קריאה בלבד, ו-PR רק דרך אישור (כמו היום).
- **מחיקה וייצוא:** כפתור אחד מוחק הכול, כולל ביטול טוקנים אצל הספקים.
- **יומן ביקורת לכל חברה:** מי ביקש מה ומה נכתב, בלי תוכן הפגישה (כמו `turn-log` היום).

## ספקים שאנחנו משלמים עליהם

Anthropic, Deepgram ו-Attendee/Recall:
- **ברירת מחדל (מומלץ):** החשבונות שלנו, עם מכסות ומדידה לכל חברה. זו ההתקנה הכי פשוטה ללקוח.
- **לארגונים גדולים:** אפשר לחבר מפתח משלהם (BYO key), כך שהנתונים עוברים רק דרך החשבון שלהם.
